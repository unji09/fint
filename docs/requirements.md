# F!nt 요구사항 명세서

## 1. 문서 개요

### 1.1 문서 목적

본 문서는 F!nt(B2B 영업 CRM)의 **사용자 관점 요구사항**을 정의한다. 시스템이 **누가 왜 이 기능을 필요로 하는가**와 **수락 기준(Acceptance Criteria)**을 기술한다. 기술적 구현 상세는 별도의 기능 명세서에서 다룬다.

### 1.2 권한 체계

| 역할 | 코드 | 설명 |
| --- | --- | --- |
| 관리자 | `ADMIN` | 최상위 관리자. 조직 전체 R/W 및 팀/사용자 관리 권한 |
| 팀장 | `MANAGER` | 팀 단위 관리자. 소속 팀 전체 데이터 R, 팀원 배정/이관 W |
| 사원 | `MEMBER` | 영업사원. 본인이 owner인 데이터 R/W |
| 개발자 | `DEVELOPER` | 시스템 모니터링/성능 대시보드 등 운영 관점 접근 |

### 1.3 우선순위 정의

우선순위는 **P등급 × 중요도** 두 축으로 표시. 예: `P0-H`.

**P등급 (개발 시점 구분)**

| 등급 | 정의 |
| --- | --- |
| P0 | MVP 필수. 이 기능 없이는 제품으로 성립 불가 |
| P1 | MVP 이후 단기 출시 (v1.0) |
| P2 | 중기 (v1.1+) |
| P3 | 확장 가능성 (로드맵) |

**중요도 (같은 P등급 내 순서)**

| 등급 | 정의 |
| --- | --- |
| H (High) | 해당 P등급 내 최우선 착수 |
| M (Medium) | 기본 |
| L (Low) | 같은 등급 내에서는 후순위 |

### 1.4 대상 권한 표기

각 기능에 해당 기능을 **사용/수행하는 주체**를 `대상` 열에 표시.

- `관리자`, `팀장`, `사원`, `개발자`, `전체`(모든 권한), `시스템`(자동 실행)

### 1.5 핵심 용어

| 영문 | 한글 UI | 정의 |
| --- | --- | --- |
| Tenant | 테넌트(회사) | 서비스 계약 단위. 데이터 격리의 기준 |
| Account | 고객사 | 영업 대상 회사 |
| Contact | 담당자 | 고객사 소속 개인 |
| Deal | 영업건 | 판매 또는 제안 진행 단위 |
| Activity | 활동 | 미팅, 통화, 메모 등 고객과의 접점 기록 |
| Wiki | 위키 | Contact/Account에 대한 AI 추출 + 수동 편집 누적 문서 |
| Signal | 시그널 | 뉴스, DART 공시 등 외부 이벤트 |

### 1.6 Deal 스테이지 정의

| 코드 | 한글 UI | 설명 |
| --- | --- | --- |
| `LEAD` | 발굴 | 초기 리드. 검증 전 단계 |
| `QUALIFIED` | 검증 | 예산/결정권자 확인 완료 |
| `PROPOSAL` | 제안 | 제안서 전달 |
| `NEGOTIATION` | 협상 | 가격/조건 협상 진행 |
| `WON` | 수주 | 계약 성사 |
| `LOST` | 실주 | 계약 실패 |

## 3. 전제/제약 사항

### 3.1 기술 전제

- 모든 비즈니스 데이터는 `tenant_id` 필드로 격리된다. 쿼리에서 `tenant_id` 누락 시 시스템은 예외를 발생시킨다.
- PostgreSQL 쓰기는 Spring Boot만 수행하며, FastAPI는 읽기 전용 접근을 가진다.
- 파일 업로드는 S3 Pre-signed URL 방식으로 서버 부하를 최소화한다.
- LLM 응답은 Redis에 캐싱되어 비용을 절감한다.

### 3.2 성능 요구사항

- 동시 접속자 150명 환경에서 p95 응답시간 500ms 이하 유지
- 최대 500명(5개사 × 100명) 수용

### 3.3 보안 요구사항

- 이관/권한 변경/고객 Export는 감사 로그(audit log) 필수 기록
- 타 테넌트 데이터 접근 시도는 즉시 차단 + 로그 기록
- 기기 일정/연락처 수집은 사용자 명시 권한 획득 후에만 수행
