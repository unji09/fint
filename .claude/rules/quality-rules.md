# 설계 원칙

## SOLID (우선순위 순)
1. **SRP** — 클래스/메서드가 너무 많은 일을 하고 있지 않은가?
2. **DIP** — 결합도가 높아 테스트/수정이 어렵지 않은가?
3. **LSP** — 자식 클래스가 부모의 의도를 왜곡하지 않는가?

## 오버 엔지니어링 경계
- 기준: "나중에 고치기 쉬운가?", "읽기 편한가?"
- 기술 선택/구현 방식 결정 시 "이게 진짜 필요한 선택인지" 여러 번 자문
- 단순 필드 할당(`this.field = param`) 수준 로직에 별도 단위 테스트 파일 생성 금지 — 서비스 테스트로 충분
- 기존 테스트가 이미 커버하는 범위인지 확인 후, 빈 곳만 추가
- 리팩토링 범위를 최소화: 목표와 직접 관련 없는 코드 개선 금지

# 품질/정리 규칙

- 동작 여부만 통과시키는 변경 금지
- 하드코딩 금지 → 상수화, 환경변수, 설정 파일 사용
- 오타 금지
- 사용하지 않는 import/field/메서드 제거
- 중복 코드 제거
- 리팩토링 시 API 스펙/네이밍 일관성 유지
- 컨벤션 위반 발견 시 기능 추가보다 리팩토링 우선

# 테스트 규칙

- 변경에 대한 단위 테스트 필수
- 계층 이동/이벤트 처리 변경 시 통합 또는 슬라이스 테스트 추가
- 테스트 생략 시 PR에 사유 명시

# PR 필수 확인 항목

- 서비스/핸들러 책임 분리 여부
- DTO/Response 분리 여부
- 트랜잭션 범위 적절성
- 입력 값 검증
