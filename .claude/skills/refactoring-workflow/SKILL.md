# 리팩토링 워크플로우

## 작업 진행 원칙

### 오버엔지니어링 경계
- 매 기술 선택마다 "이게 진짜 필요한 선택인지" 자문
- 단순 필드 할당 수준 로직(`this.field = param`)에 별도 테스트 파일 불필요
- 기존 테스트가 커버하는 범위 먼저 확인 → 빈 곳만 추가
- 리팩토링 목표와 직접 관련 없는 코드 개선 금지

### 변경 범위 최소화
- 한 번에 하나의 관심사만 변경
- 의존 관계가 적은 것부터 순서대로 진행
- 각 단계 완료 후 `./gradlew test`로 기존 테스트 통과 확인

## 산출물 형식

### 커밋 메시지
- 작업 완료 시 커밋 메시지를 사용자에게 제시 (자동 커밋 금지)
- 형식: `refactor: 변경 요약` (한 줄)

### Before/After 요약
리팩토링 완료 시 아래 형식으로 변경 내용 정리:
문제 (Before)

어디에 어떤 문제가 있었는지
그로 인해 발생하는 구체적 이슈

해결 (After)

어디를 어떻게 변경했는지
변경으로 인한 효과

수정 파일 요약
파일변경 유형......
### 면접 관점 정리
- 기술 선택에 대한 논리적 근거 설명 가능해야 함
- "왜 이 순서로 진행했는가" — 구조적 근거 필요
- "왜 이 방식을 선택했는가" — 대안 비교 근거 필요
- "이 변경의 효과는 무엇인가" — 결합도/응집도/테스트 용이성 등 구체적 지표

## 리팩토링 Phase 순서 논리

구조(1→2→3) → 검증(4) → 성능(5) 순서를 따른다.

| Phase | 주제 | 순서 근거 |
|-------|------|----------|
| 1 | 글로벌 예외 처리 체계 | 가장 광범위한 인프라. 이후 모든 Phase에서 사용 |
| 2 | Entity-DTO 의존 방향 수정 | Phase 1 예외 체계 위에서 안전하게 진행 가능 |
| 3 | Controller 계층 책임 분리 | Entity/DTO 경계 확립 후 Controller 정리 |
| 4 | Request DTO 입력 검증 추가 | 계층 구조 확립 후 경계에서 검증 추가 |
| 5 | N+1 쿼리 해결 | 구조 안정화 후 성능 최적화 |

## TDD 적용 기준

리팩토링에서 TDD는 "변경이 기존 동작을 깨뜨리지 않음"을 보장하는 데 초점:

1. **기존 테스트가 있는 경우**: 기존 테스트가 깨지면 수정, 안 깨지면 추가 테스트 불필요
2. **기존 테스트가 없는 경우**: 변경 대상의 핵심 동작에 대해서만 테스트 추가
3. **단순 시그니처 변경**: 서비스 레벨 테스트로 충분 — Entity 생성자 단위 테스트 불필요
