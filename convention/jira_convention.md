## 1. 에픽(Epic) 카테고리 규칙

에픽 이름 앞에 **대괄호 카테고리**를 반드시 명시한다.

| 카테고리 | 설명 | 예시 |
| --- | --- | --- |
| **[기획]** | 아이디어, 시장조사, 기능명세서, 프로젝트 규칙 등 | `[기획] 기능 명세서` |
| **[설계]** | API 명세서, 화면설계, DB 설계, 아키텍처 설계 | `[설계] API 명세서` |
| **[BE]** | 백엔드 개발 (서버, API 구현, DB 연동) | `[BE] 통화 분석 API 개발` |
| **[FE]** | 프론트엔드/앱 개발 (UI 구현, 화면 연동) | `[FE] 홈 화면 구현` |
| **[INFRA]** | 인프라 구축, CI/CD, 배포, 서버 설정 | `[INFRA] Jenkins 파이프라인 구축` |
| **[학습]** | 프로젝트에 필요한 기술 학습 및 정리 | `[학습] Kafka & Spark 학습` |
| **[APP]** | 앱 프론트엔드 개발 | `[APP] 녹음 화면 구현` |

## 2. 이슈 계층 구조

```
Epic (에픽)          → 큰 기능 단위 or 업무 묶음
  └─ Sub-task     → 스토리를 쪼갠 세부 작업
```

### 네이밍 컨벤션

- **에픽**: `[카테고리] 업무 묶음명`
    - 예: `[설계] API 명세서`
- **태스크**: `[커밋 유형]: 작업 내용` (하나의 mr과 동일시 되는 것을 권장)
    - 예: `[feat]: 통화 녹음 API 엔드포인트 정의`

| 커밋 유형 | 의미 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 코드 리팩토링 |
| `test` | 테스트 코드 추가, 수정, 삭제 |
| `chore` | 빌드, 패키지 매니저 관련 수정 (Dockerfile, gradle, sh, yml 등) |
| `docs` | 문서 추가, 수정, 삭제 |
| `!Hotfix` | 급하게 치명적인 버그를 수정할 때 |

| 지라용 추가 유형 | 의미 |
| --- | --- |
| `design` | 시스템 설계 ex) 플로우차트, ERD, 화면정의서 등  |
| `plan` | 기획 아이디어 관련 회의 |
| `study` | AI 특강 프로젝트할 때 |

## 3. 스토리 포인트 기준

**기준점: 4 SP = 하루(8시간) 온전히 집중해야 하는 작업량**

| SP | 소요 시간 감각 | 난이도 | 예시 |
| --- | --- | --- | --- |
| **1** | ~1-2시간 | 단순 반복, 즉시 완료 가능 | 회의록 정리, 간단한 설정 변경, 문서 오타 수정 |
| **2** | ~반나절 (3-4시간) | 약간의 고민 필요, 익숙한 작업 | 기존 API에 필드 추가, 유사 서비스 1개 분석, 학습 내용 정리 |
| **3** | ~반나절~하루 (5-6시간) | 조사/검토가 필요한 작업 | 기능 명세서 초안 작성, 화면 와이어프레임 1개 |
| **4** | ~하루 (8시간) | 집중 필요, 구현+테스트 포함 | API 명세서 작성, 간단한 CRUD API 구현, Figma 화면설계 |
| **5** | ~1.5일 (10-12시간) | 복잡한 로직 or 여러 요소 연동 | 로그인/인증 플로우 구현, 복잡한 화면 구현 |
| **6** | ~2일 (14-16시간) | 높은 복잡도, 리서치 병행 | 실시간 통화 분석 파이프라인 구현, 외부 API 연동 |
| **8** | ~3일 이상 | ⚠️ **분할 권장** | 스토리를 더 작은 단위로 쪼갤 것 |

### 포인트 배정 원칙

1. **8 이상은 무조건 쪼갠다** — 하나의 스토리가 8 이상이면 2개 이상으로 분할
2. **불확실성이 높으면 +1** — 처음 해보는 기술이면 한 단계 올려 배정
3. **팀원 간 상대적 일관성 유지** — 같은 유형의 작업은 같은 포인트
4. **리뷰/피드백 시간도 포함** — 작성 후 팀 검토까지 고려

## 5. 스프린트 운영 규칙

### 스프린트 주기

- **1주 단위** 스프린트 운영 (월~일)
- 스프린트 이름: `N주차 스프린트` (예: 1주차 스프린트)

### 스프린트당 권장 포인트

- 팀원 1인당 **스프린트 velocity 목표: 16~20 SP/주**
    - 하루 평균 약 3~4 SP (= 순수 개발/작업 시간 6~8시간)
    - 회의, 리뷰 등 오버헤드 고려하여 현실적으로 설정

### 스프린트 의식(Ceremony)

| 활동 | 시점 | 내용 | 행동 |
| --- | --- | --- | --- |
| 스프린트 플래닝 | 월요일 오전 | 이번 주 할 일 선정 + SP 확인 | 백로그 or 목록에 할일 작성 및 에픽 배정 + 스토리 포인트 배정  |
| 스프린트 시작 | 스프린트 플래닝 이후 | 백로그에 스프린트 배정 | 팀장이 스프린트 시작(활성화) 누르고 팀원들이 백로그에 스프린트 배정 |
| 데일리 스크럼 | 매일 오전 (10분) | 어제 한 일 / 오늘 할 일 / 블로커 |  |
| 스프린트 리뷰 | 금요일 오후 | 완료된 작업 데모 + 검토 |  |
| 회고 | 금요일 마무리 | 잘한 점 / 개선점 / 액션아이템 |  |

## 6. 워크플로우 상태

```
할 일 → 진행중 → 완료
```

| 상태 | 의미 | 기준 |
| --- | --- | --- |
| **To Do** | 할 일 | 스프린트 백로그에 배치 |
| **In Progress** | 작업 중 | 담당자가 작업 시작 |
| **Done** | 완료 | 리뷰 통과 + merge 완료 |

## 7. 담당자 배정 규칙

1. **모든 서브테스크(파랑)에 담당자 1명** 반드시 지정 (책임 소재 명확화)
2. 에픽에 담당자 필수 지정 X
3. 페어 작업 시 → 같은 내용의 서브테스크 2개 만들기
